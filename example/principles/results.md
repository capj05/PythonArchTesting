### `err_total_area_isinstance`: the client branches on the type of an object instead of calling its method

**What:** Function `total_area` (report.py:8) asks which class an object is: on line 11 of `report.py` it calls `isinstance()`.

**Why:** Every kind of object already knows how to do the job: that is what its method is for. A chain of `isinstance` tests repeats the work of the classes outside them, and every new kind needs another branch here; a kind the chain forgets is handled wrong or not at all.

**Fix:** Call the method the base class declares (the same call for every object) and move the code of each branch into the method of its class.

### `err_describe_all_type`: the client asks for the type of an object with `type()` instead of calling its method

**What:** Function `describe_all` (report.py:13) asks which class an object is: on line 16 of `report.py` it calls `type()`.

**Why:** Comparing `type(x)` with a class, or its name `type(x).__name__` with a string, is the same branching on the type as `isinstance`, and it is stricter still: an object of a class derived from the one compared with does not pass the test.

**Fix:** Call the method the base class declares (the same call for every object) and move the code of each branch into the method of its class.

### `err_square_no_base`: a variant does not derive from the base class

**What:** Class `shapes:Square` (shapes.py:44) does not derive from the base class `shapes:Shape`.

**Why:** The class has the methods, but nothing states that it is a kind of the base. The base cannot require it to implement every method, and a reader or a tool cannot see that it may be used wherever the base is expected.

**Fix:** Derive the class from the base class: name the base in parentheses after the class name.

### `err_shape_concrete`: the base class is not abstract

**What:** Class `shapes:Shape` (shapes.py:6) should be an abstract base class, but it declares no abstract method; it defines these methods as ordinary ones: area, describe.

**Why:** A base class whose methods are ordinary ones can be instantiated by mistake, and a variant that forgets to implement a method inherits the base's version: the mistake shows only when that method is called (or never, when the base's version returns something), instead of when the variant is created.

**Fix:** Derive the base from `ABC` (module `abc`) and mark each method every variant must implement with `@abstractmethod`.

### Gap protocol_base: a base written as a `typing.Protocol` without `@abstractmethod` counts as concrete

is_abstract_class knows an abstract method only by its decorator (`@abstractmethod`), so a base derived from `typing.Protocol` whose methods have the body `...` fails as concrete_base, although Python refuses to create an object of a protocol class too. A protocol whose methods are marked `@abstractmethod` passes. The variants must still name the protocol as their base: a variant that only has the same methods, without deriving from it, is not_a_subclass, because the principle taught is inheritance.

### Gap type_test_without_a_call: a branch on the type that calls nothing: `match` with a class pattern, `obj.__class__`

forbid_runtime_calls sees the calls `isinstance()` and `type()`. A `match` statement with a class pattern (`case SomeClass():`) and a comparison of `obj.__class__` test the type without calling either, so a client that branches that way passes.

### Gap duck_typing: a branch on what an object has instead of what it is: `hasattr`, `getattr`, catching `AttributeError`, reading a variant's own data

forbid_runtime_calls sees the calls `isinstance()` and `type()`. A client that asks whether an object has an attribute (`hasattr(obj, "x")`, `getattr(obj, "x", None)`, `try: ... except AttributeError`) and then computes by itself from the data of a variant (`obj.x * obj.y`) branches on the kind of the object just the same, but makes neither call, so it passes. The check promises only that the client does not test the class of an object.

### `err_total_ignores_discount`: the code doing the job does that part of it by itself instead of calling the object it was given

**What:** Method `PriceCalculator.total` (pricing.py:10) never calls the interchangeable object it was given (`self.discount`): it does that part of the job by itself, or branches on which kind of object it has.

**Why:** The object exists to do this part of the job, but the code ignores it and computes by itself, usually in a chain of `if` branches over the kinds it knows. A new kind then needs another branch here, and a kind the code does not know is silently handled wrong.

**Fix:** Call what the constructor stored (the same call for every kind) and move the code of each branch into the class or function of its kind.

### `err_calculator_builds_discount`: the code doing the job builds its interchangeable object itself

**What:** `pricing:PriceCalculator.__init__` builds its own object of `discounts:PercentDiscount` (line 8 of `pricing.py`) instead of using the one it was given.

**Why:** Whoever creates the code doing the job should choose the way it is done. Code that builds its object itself always does the job the same way, whatever it was given, and cannot be tried out with another object.

**Fix:** Keep the object the constructor gets as a parameter (`self.x = x`) and let the code that creates this object choose and build the interchangeable one.

### `err_total_isinstance_fallback`: the code doing the job asks which kind of object it was given

**What:** Method `PriceCalculator.total` (pricing.py:10) asks which kind of object it was given: on line 14 of `pricing.py` it calls `isinstance()`.

**Why:** The code calls what it was given only for the kinds it does not test for; the kinds it tests are computed here, often from their data. A new kind needs another branch here, and every kind must do its part of the job twice: once in its own class and once in this branch.

**Fix:** Remove the test of the kind: call what the constructor stored for every kind, and move the code of each branch into the class or function of its kind.

### Gap hardcoded_function: code that keeps a function of its own instead of the one it was given is classified as no_delegation

forbid_runtime_instantiation sees objects of classes being built. When the interchangeable behaviour is a plain function, code that ignores the function it was given and uses one it names itself (`self.x = some_function`) builds nothing, so hardcoded_strategy is not found. It is still caught: the given function (the spy) is never called, so require_runtime_delegation fails and the finding is no_delegation, whose advice fits it only in part. A future check would need to tell what the constructor stores apart from what it was given (a stored attribute that is no parameter and refers to a function bound to the strategy role), so that a function chosen inside the code counts as hardcoded_strategy too.

### Gap result_discarded: code that calls the object it was given but throws away what it returns is not found

require_runtime_delegation sees whether the given object (the spy) is called, not what is done with its answer. Code that calls it and then computes the result by itself (`self.x.apply(amount)` as a statement of its own, then `return amount * 0.9`) delegates as far as the check can tell, so it passes. The spy returns no real answer, so its result cannot be followed through the code either; a future check would need to compare the result of the context with the result of the strategy it was given.

### Gap unmatched_class_by_method_name: a helper class beside the interchangeable classes that has a method named like theirs is classified as hardcoded_strategy

A class the code doing the job builds, which no class of the reference matches, is taken for an interchangeable one when it lives in their module and has one of them (or their common interface) among its bases, or defines a public method named like one of theirs. The likeness is by name only: a helper class of that module that happens to have such a method counts too, and a new interchangeable class with no such base and only differently named methods does not (it could not stand in for the others anyway). Exceptions never count. A future check would need to tell, from how the object is used, whether the code doing the job calls it in place of the one it was given.
